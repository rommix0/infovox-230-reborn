# AGENTS.md: Infovox 230 disassembly project

This project reverse-engineers the **Infovox 230** text-to-speech engine (`bin/Ivx230nt.dll`, Telia Promotor AB, 1996–1998). It's a RULSYS-family rule-based formant synthesizer from the KTH (Carlson and Granström) lineage, packaged as a Microsoft SAPI 4 COM engine.

**The goal is a standalone engine**, the `infovox230` library (`include/infovox230.h`) plus `ivxsay`, not a SAPI engine. The SAPI 4 layer is not a target (see the ground rules).

Read **`REFERENCE.md`** first. It has the paper summaries, every confirmed address and table, and a paper-vs-binary cross-reference with confidence tags.

## Ground rules

- **The Ghidra phase has started** (project `ivx_ghidra`, reached through the ghidra-mcp tools). The goal is C code that compiles. **Don't rename things by hand in the GUI only.** Put every name, prototype and struct in `tools/ghidra/symbols.tsv` or `gen_types.py`, then re-run `IvxApply.java`, so the knowledge base stays reproducible. The Python tools (pefile, capstone) still work for quick checks.
- **Toolchain:** 32-bit gcc 14.2 (winlibs) is at `C:\winlibs\mingw32\bin`. It isn't on PATH, so use `export PATH=/c/winlibs/mingw32/bin:$PATH`. `C:\winlibs\mingw64` holds the 64-bit build.
- **Tag every claim** as `[CONFIRMED]`, `[LIKELY]`, `[HYPOTHESIS]` or `[NOT FOUND]`, matching `REFERENCE.md`. Don't promote a hypothesis to confirmed without citing the address or data that proves it.
- **Distinguish VA from file offset.** `strings -t x` and `xxd` print *file offsets*. Code and xrefs use *VAs*. Section map:

  | Section | VA | File offset (raw) |
  |---|---|---|
  | `.text` | 0x10001000 | 0x400 |
  | `.rdata` | 0x10040000 | 0x3ee00 |
  | `.data` | 0x10044000 | 0x42a00 |
  | `.rsrc` | 0x10054000 | 0x4f800 |

  So a VA in `.data` is `file offset − 0x42a00 + 0x10044000`.
- **SAPI is a non-goal.** The COM/SAPI layer (`0x10001000–0x10012xxx`: `CEngine`, `CAudioDev`, `CEnumFactory`, the registry and audio-device code) is not ported. Read it only where it shows how the engine drives RULSYS (as it did for the `tp_putc` resend protocol, the stop sequence and the bookmark serials); otherwise label it and skip it, like the licensing code.
- **Licensing and copy protection** (Sentinel dongle, Crypkey, `IVX230.LIC`, `DEVELOP` / `NTHDEMO` / `STHDEMO`) has already been cracked in this copy so it runs on modern systems. It isn't relevant to the speech work, so just label that code and skip it.
- Don't modify anything in `bin/` or the papers in `docs/`. Our own design documents go in `docs/superpowers/specs/` (`YYYY-MM-DD-<topic>-design.md`).

## Tools (`tools/`)

Run them from `tools/`. They use Python 3.13 with `pefile` and `capstone`.

```bash
python ivxdis.py full.asm xref.json
```

This linearly disassembles `.text` into `full.asm`, annotated with imports and inline string literals, and writes `xref.json` (call-target counts and immediate-operand xrefs). Regenerate it after changing the script.

```bash
python xr.py 0x100490d0 0x10049500
```

This lists the code addresses that reference any VA in the given range.

```bash
python rng.py 100245e0 10024940
```

This prints the disassembly between two VAs (hex without `0x`), skipping nop/int3 padding.

```bash
python ops.py > ops.txt
```

This emulates the rule-interpreter dispatch in `cw_step` (`0x10020240`) and prints `opcode → handler` for every opcode 0x00–0x1FC.

```bash
python ivx.py ../bin/swrules.ivx
```

This prints the `.ivx` directory and every phoneme/symbol record with its parameter and variable items.

```bash
python ivxdasm.py
```

With no arguments, this validates the opcode operand-size table. Every rule in every `.ivx` file must decode to exactly its length prefix; currently 15,564/15,564 do. Re-run it after touching `SZ`/`opsize`.

```bash
python ivxdasm.py ../bin/gerules.ivx 12
```

This prints a readable listing of the rule modules (section numbers 9, 10, 12, 5, 6, 11 = M0–M5; default = all), with phoneme names, feature masks, parameter@time specs and fixed-point factors. Saved listings are in `tools/out/`.

```bash
python failing.py ../bin/xx.ivx <sec> [n]
```

This shows rules that don't decode cleanly, with a raw word dump. Use it when extending the opcode table.

Ghidra knowledge base (`tools/ghidra/`):

```bash
python gen_types.py
gcc -std=c11 -fsyntax-only ivx_types_check.c
```

The first command regenerates `ivx_types.h` and `ivx_types_check.c` from the offset tables in `gen_types.py`. It fails on any overlap or size overflow. The second runs with 32-bit gcc and asserts every field offset.

To apply everything to Ghidra, copy `IvxApply.java` to `%USERPROFILE%\ghidra_scripts\` and run it with ghidra-mcp `run_ghidra_script` (script_name `IvxApply.java`, program `Ivx230nt.dll`). It is idempotent and prints `errors: 0` on success. Save the program afterwards.

- **`IvxApply.java` kinds:** `func`, `data` and `label`. There is also `nofunc`, which deletes a bogus function (for example a switch case that analysis split off) and re-absorbs its code into the parent function.
- **`IvxExport.java <out.c> [tag…]`** writes the decompiled C of every function with the given tags (default `RULSYS`), for example `src_opsmooth`. It's useful for bulk reading and as the starting point for the C port.

C port (repo root, with 32-bit gcc on PATH):

```bash
make test
```

This builds `src/*.c`, the five DLL-differential tests in `tests/`, the `infovox230` library, `api_test` and `ivxsay`. It runs the five tests against `bin/Ivx230nt.dll` and `api_test` against the library, and each must print `0 failures`. Then `tools/check_ivxsay.py` requires `ivxsay` to reproduce the DLL-verified audio in all 12 languages. `python tools/gen_synth_data.py`, `gen_op_data.py` and `gen_tp_data.py` regenerate `src/synth_data.c`, `src/op_data.c` and `src/tp_data.c`, and `make` runs them automatically when the DLL or the script is newer.

- **Hooking in tests:** to test a function that runs inside the DLL pipeline, patch a `jmp` to a hook into the loaded DLL (`patch_jump`). Keep a `trampoline(va, n)` to call the original, where n covers whole prologue instructions without relative operands.
- **Comparing state:** the hook copies the Core and pool with `image_take`, runs the original and the port, and compares them with `compare_core_pool`.
- **Nesting:** hooks nest, so guard them with a depth counter. Keep `-msse2 -mfpmath=sse`, because the table builders are only bit-exact with double (not x87 extended) math.

Known limitations:

- Linear sweep can misalign in data islands such as switch tables inside `.text`.
- Functions are found from call targets or `push ebp; mov ebp,esp`. The optimised (non-synth) code often has no frame pointer, so walk back to nop/int3 padding to find function starts.

## Established facts to build on

These are confirmed. Details are in `REFERENCE.md` §3 (synth) and §5 (`.ivx`).

- The synth has 21 parameters in this order: `F1 B1 F2 B2 F3 B3 F4 B4 FH K1 C1 K2 C2 FN BN AK AC AH AN A0 F0`. The rules' full phonetic vector adds `DR ST FS CS FD` in front.
- Frequency parameters are **quarter-tone indices**, `F = 200·2^((k−3)/24)` Hz with k = 0…127. Bandwidths are **additive ΔB indices** into a 32-entry table over the default `B(F)=√((F/20)²+50²)`. Amplitudes are **dB, 0…31**, with 31 = 0 dB.
- The source is an **impulse per pitch period** plus a 16-bit LFSR noise source. The output passes a **200 Hz one-pole low-pass**. This is the OVE III design, not GLOVE and not LF.
- Default speed (150 wpm) is **100 frames/s, or 10 ms frames**. The engine's speed setting changes the synth frame rate (`IVX_FRAME_RATE` in the library; the rules' "rate", `tts_ctrl` 9, is a voice parameter, not speed).
- There's no floating-point prosody code anywhere. **Prosody is rule bytecode in the `.ivx` files.** KIM is confirmed in `gerules.ivx` M2 (6 % downstep, 95 Hz floor, ×1.08 close-vowel summit, 130 Hz start). Swedish uses Hz target points too, not Fujisaki.
- `.ivx` files are big-endian. The body directory is `H[0..15]`, and phoneme ids are record offsets from `H[8]`. The rule bytecode is a pattern-match/rewrite machine (`RULE len … NEXT #rule`) with a small accumulator arithmetic unit. See `REFERENCE.md` §5.
